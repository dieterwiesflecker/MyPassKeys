# Token Signing & KEK Management

## Key storage structure

`Tenant.JwtKeys` is a `List<JwtKeyEntry>`. Each entry has `PrivateKey` and `PublicKey` as `JsonElement` fields (stored as JSONB in Marten/Postgres), plus `Kid`, `IsActive`, and `CreatedAt`. Only one key is active for signing; retired keys remain for validation.

## Private key encryption at rest

**Private keys are envelope-encrypted at rest** (`IKeyProtector` / `AesGcmKeyProtector` in `KeyProtector.cs`): `PrivateKey` holds an AES-256-GCM blob `{"enc":"A256GCM","kek":<id>,"iv","ct","tag"}` rather than the plaintext JWK, so a Postgres/Redis dump alone cannot forge tokens. The KEK comes ONLY from config (`MyPassKeys:KeyEncryptionKey`, base64 32 bytes — required, startup fails fast without it); the entry's `Kid` is bound as AES-GCM AAD so blobs can't be swapped between key entries. `PublicKey` stays plaintext (JWKS needs it).

All key creation goes through `TenantEndpoints.CreateKeyEntry(IKeyProtector)` (encrypts) and the only decrypt is in `TokenService.GenerateTokenAsync` via `keyProtector.Unprotect(...)` just before signing — do NOT add code paths that read `PrivateKey` directly as a JWK. `Unprotect` passes legacy plaintext JWKs through (pre-migration docs / stale cache); an idempotent startup migration in `Program.cs` re-encrypts any plaintext or previous-KEK key and invalidates the tenant cache.

Losing the KEK makes all signing keys unrecoverable — tenants would need `/rotate-key` + a config wipe of dead entries. This protects against DB-level attackers only; an app-server compromise still exposes the KEK.

## Forced re-key / verify-before-retire — `POST /admin/rekey`

`AdminEndpoints` (installation-wide, restricted to a `tenantadmin` of the **management** tenant via the `tenant_id` claim, same gate as `PortalEndpoints`). It runs `KeyRotationMaintenance.RekeyAllUnderCurrentKeyAsync`, which walks **every** tenant's signing keys and all six sealed document types and re-encrypts / re-seals anything not already on the current KEK — the same idempotent work the two startup migrations do, but on demand and returning **per-type counts**. Purpose: after a KEK rotation, call it and confirm `fullyOnCurrentKey: true` (all counts 0) **before** removing the old KEK from `PreviousKeyEncryptionKeys`, so you never retire a KEK that some blob or seal still depends on.

It shares the startup migration's documented exception to the "seal/verify only in `Fido2MartenDbService`" invariant (raw Marten session, because it re-seals already-sealed docs) and still obeys the core rules: verify seal + rollback anchor before re-sealing, record anchors only after `SaveChangesAsync`, invalidate the tenant cache for every touched tenant.

## KEK rotation runbook (zero-downtime, `./deploy.sh` / Docker)

The two keys are wired through the server's `.env` (in `$REMOTE_DIR`, which Compose reads for `${...}` interpolation). `compose.prod.yaml` maps `KEY_ENCRYPTION_KEY` → `MyPassKeys__KeyEncryptionKey` (the current KEK, auto-generated by `deploy.sh` if missing) and `PREVIOUS_KEY_ENCRYPTION_KEY` → `MyPassKeys__PreviousKeyEncryptionKeys__0` (the previous KEK, normally unset → empty → ignored by `KekConfig.Load`).

**Rotation is driven entirely by `deploy.sh` subcommands — never SSH in to hand-edit `.env`.**

1. `./deploy.sh rotate-kek` — moves the current `KEY_ENCRYPTION_KEY` to `PREVIOUS_KEY_ENCRYPTION_KEY` and generates a fresh current key (all in the server `.env`, keys never touch the local machine), then restarts just the `mypasskeys` container (`up -d --force-recreate --no-deps`, no rebuild/upload). The startup migrations re-encrypt signing keys and re-seal documents under the new KEK, reading old blobs via the previous KEK.
2. Call `POST /admin/rekey` from the management portal (management-tenant `tenantadmin`) and confirm `fullyOnCurrentKey: true` with every count 0. If not, it just re-keyed stragglers — re-run until clean.
3. `./deploy.sh retire-kek` — removes `PREVIOUS_KEY_ENCRYPTION_KEY` from the server `.env` and restarts the container. It prompts first (set `FORCE=1` to skip) because once the old KEK is gone, any blob still on it is unreadable — step 2 is what proves that can't happen. Keep only two live KEKs (current + one previous); each retired key is another copy of a secret that can still decrypt data.

A plain `./deploy.sh` (no args) still does a normal full deploy and only *seeds* `KEY_ENCRYPTION_KEY` if absent — it never rotates. For a non-Docker / standalone run the same applies via `MyPassKeys:KeyEncryptionKey` and `MyPassKeys:PreviousKeyEncryptionKeys` in config (or the `MyPassKeys__...` env vars).

## Key reconstruction

- `TokenService.ResolveSigningKey()` reconstructs `ECDsa` from JWK parameters (`D`, `X`, `Y`) since `JsonWebKey` alone lacks the crypto provider for signing.
- `TokenService.ResolveValidationKey()` reconstructs `ECDsa` from public-only parameters (`X`, `Y`).
- Key pairs generated via `ECDsa.Create(ECCurve.NamedCurves.nistP256)` with a `kid` for JWKS identification.
